# add 写入路径失效的定位与修复 — 2026-10-13

dsh-mcp-manager **v0.4.2**(本仓库,master;`f43b5bf` + `100cd4d`)

起因:用户要求在插件里安装 `@upstash/context7-mcp`,以验证插件能否正常使用。结论是
**不能**——`mcp_manager_add`、`cli add` 与面板 add 框对**全新服务器从未成功过**,而且会给出假绿灯。

## 1 实测证据(修复前,v0.4.1)

| 检查 | 结果 |
|---|---|
| `add` dry-run 预览 | 形状已不对:没有 `config:` 头,配置字段平铺成条目同级 |
| `confirm:true` 落盘 | 顶层裸条目 `- id: mcp-context7`,`config:` 缺失 |
| 插件自身读回(`list` / `list --json`) | 该行三列全空 / `"config": {}` |
| `probe mcp-context7`(读文件) | `FAIL: unknown transport: undefined` |
| `add` 当场回报 | **`probe OK: 2 tools`** ← 假绿灯 |
| 官方方言 `cordis-composition-reference__SKILL.md:15-16` | 带 `id` 无 `insert` 的补丁按 id 覆盖已有行;匹配不到者 **warned about and skipped** |

`add` 当场回报成功、而读回是空配置,这两条同时成立——说明探活测的不是落盘内容。

## 2 根因(4 处实现 + 1 处文档漂移)

| 编号 | 缺陷 | 位置 | 修复 |
|---|---|---|---|
| D1 | `renderEntryRow()` 只渲染配置体,从不输出 `config:` 头 | `lib/patchfile.js` | `configLines` 恢复"相对行"约定并补 `config:` 头 |
| D2 | `appendEntry()` 追加顶层裸条目,loader 永不挂载 | `lib/surgery.js` | `renderInsertBlock()` 写入独立 `- insert:` 块(纯追加,不动已有字节) |
| D3 | 写后探活测内存对象而非落盘行 | `lib/tools-bridge.js`、`lib/server.js`、`cli/mcp.js` | `readBackEntry()`;三入口改为校验并探活落盘行 |
| D4 | 单测只断言 `includes('serverName: delta')`,平铺形状同样满足 | `test/patchfile.test.mjs` | 新增"写入→读回"往返回归测试 |
| D5 | README 与设计文档承诺 `failOnStartupError: true`,实现从未写 | `lib/resolve.js` | 唯一漏斗 `finish()` 统一默认 true,显式值不覆盖 |

后续补齐 3 处:`applySurgeryAsync` 把**解析后的候选**交给 `preCommit`(写前结构门
`appendEntryGate()`,与写后读回共用 `appendedRowProblem()`,同一把尺子量前后)、add 路径
serverName 去重(`duplicateServerNameProblem()`,**计数**判据——id 由 serverName 派生,
按 id 排除恰好会漏掉要抓的情况)、`cli add` 拒绝时改报 `FAIL ...` 而非抛栈。

## 4 安装态同步与重启(用户实测)

按 v0.4.0 惯例把 8 个文件(6 个代码文件 + `package.json` + `README.md`)同步进
`~/.dsh/profiles/desktop/node_modules/@dsh-contrib/dsh-mcp-manager`;同步后逐文件哈希比对,
**剩余差异 0**,`package.json` = 0.4.2。技能文件两边哈希一致(`6894E9DB…`),无需同步。

**同步不足以生效**:同步之后,同样的 dry-run 仍输出旧形状(平铺、无 `config:`)。官方依据
`@deepseek-ai/dsh-plugin-manager` README:

> Package replacements require restarting the process to load a fresh JavaScript module generation.

HMR 只覆盖配置重载,不覆盖模块代码替换。重启后三项实测:

|---|---|
| 新代码是否加载 | dry-run 预览 = `- insert:` 块 + 嵌套 `config:` + `failOnStartupError: true` |
| agent 工具去重门 | 重复安装 context7 被拒;live 文件 sha256 `before == after`(逐字节未变) |
| Context7 工具 | `mcp__context7__resolve-library-id` 返回真实数据(Zod `/colinhacks/zod`,1825 片段);harness 进程起于 16:39:28,context7 服务于 16:39:34 被重新拉起 |

## 5 收尾打磨(v0.4.3)

| 问题 | 修复 |
|---|---|
| 拒绝时把管线内部措辞一并报出(`candidate failed validation (kept at …)`) | `applySurgeryAsync` 分离两种失败:loader 解析失败仍保留 `.candidate`(那才是值得看的东西);`preCommit` 语义拒绝改为**只报原因**,带 `code = candidate_rejected`,并删除 `.candidate` |
| 面板 add 对重复 serverName 返回 500(客户端错误) | `handleAdd` 采用与 `handleUpdate` 相同的映射:`FileChangedExternally` → 409,`e.code` → 400,否则 `candidate_invalid` → 400 |

CLI 侧实测:`FAIL duplicate serverName: context7 — mcp-context7 is already registered`,单行、
exit 1、无残留 `.candidate`、目标文件未变。

起未重启,`mcp__memory__read_graph` 调用成功。与 D5 同类(文档与实现不符),只是方向相反:
文档声称了一个并不存在的限制。已改为实测行为。

## 8 结论

`add` 是插件的主打功能,却因缺少形状/落点/读回三层验证而长期静默失效——上一份 e2e 记录的
"已验证"表恰好没有 `add` 一项,盲区正在此处。三层验证现已闭合:写前门、写后读回、探活对象
一致;三处预览与写入同源(`renderInsertBlock()`),预览不再可能与文件漂移。
